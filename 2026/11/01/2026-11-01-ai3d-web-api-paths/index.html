从项目早期讲起：浏览器与 Web 服务如何请求游戏后端

发表于2026-11-01|更新于2026-11-07|AI 3D 游戏生成
|总字数:1.9k|阅读时长:6分钟|浏览量:|评论数:

打开游戏工作台时，页面要读取项目和生成任务；点击交互按钮时，浏览器也可能直接发起 API 请求。两者最终都访问 NestJS 后端，但请求发起的位置不同，连接地址与 Cookie 处理方式也不同。

本文继续整理项目早期基础。对照 2026 年 8 月 3 日提交 fabfabfb，当前 apps/web/src/lib/api.ts 没有差异；next.config.ts 保留原来的转发规则，后来补充了开发来源配置。下文依据当前源码解释请求路径，不涉及近期仍在调整的 Agent 编排。

背景：相同接口，两种调用位置

当前工作台页面在服务端通过 apiFetch() 获取 /projects/<id>/workbench 等数据；评分等客户端组件则调用浏览器 fetch('/api/v1/...')。不能把这两种 fetch 当成同一个运行环境。

服务端工具文件声明了 import "server-only"，并读取当前请求的 Cookie 与后端内部地址；浏览器使用对外站点的相对路径，由 Web 转发到后端。

    flowchart TD
  A[浏览器打开工作台] --> B[Web 服务端页面]
  B --> C[apiFetch 与 apiRaw]
  C --> D[读取当前 Cookie 并请求内部地址]
  D --> E[NestJS API]
  F[浏览器按钮操作] --> G[同源 api/v1 路径]
  G --> H[Web rewrite 转发]
  H --> E
  E --> I[身份与业务检查]
  I --> J[返回结果]

图中表示两条请求路径，不表示某个操作必须重复发送两次。实际使用哪条路径取决于页面或组件的调用代码。

后端 main.ts 设置 api/v1 全局前缀，并以 cors: false 创建应用。这与当前通过 Web 暴露同源路径的设计配合使用，但不能据此把 CORS 当成访问权限控制。用户身份、项目所有权和角色仍由后端对应模块检查。

Socket.IO 也有转发规则；仅从配置存在，不能推断真实代理环境中的长连接已经验证。部署排查需要分别确认 HTTP 请求与连接升级路径。

Web 服务端的 fetch 不会因为浏览器已经登录，就自动替当前用户补上会话。这里从入站请求读取 Cookie，再写入发往后端的请求头，使后端能够识别当前用户。

也因此，这个工具应当面向可信内部后端和受控路径使用。当前实现转发的是完整 Cookie 字符串，并未只挑选单个会话 Cookie；不能把它直接扩展成向任意第三方 URL 发送用户请求的通用代理。

JSON 和文件上传的请求头不同

apiRaw() 默认添加 content-type: application/json，但遇到 FormData 时不添加。multipart 表单需要包含边界信息，让运行时生成 Content-Type 才能与实际编码匹配。

调用方传入的 init.headers 最后参与合并，因此可以覆盖前面默认的同名键。当前实现通过对象展开合并 header，不能把它描述为对所有 Headers 和元组数组输入都做了完整规范化。

这个基础工具也没有替调用方执行 JSON.stringify。项目创建 Action 会自行序列化请求对象；上传路径则直接传递 FormData。编码方式与请求头需要一起核对。

私人数据与错误如何处理

工具将 cache: "no-store" 放在 init 展开之后，因此这条请求路径明确禁用该 fetch 的缓存。它适合工作台这类依赖当前用户和实时任务状态的数据。这个配置约束的是这里的服务端请求，不等于站点所有页面、浏览器缓存或中间代理都自动采用相同策略。

上层 apiFetch<T>() 读取 JSON，解析失败时得到 null；响应状态不成功时抛出 ApiError，保留 status、message 和原解析结果 details。服务返回带 message 的 JSON 时使用其信息，否则回退到包含状态码的错误文案。

有两个实际边界：网络连接失败会在取得 Response 之前抛出，未必成为 ApiError；成功状态但没有可解析 JSON 时，函数可能返回 null，即使泛型 T 声明为某个对象。泛型并没有执行响应校验。

因此，遇到空响应、下载文件或需要读取特定响应头的操作，应核对是否需要使用返回 Response 的 apiRaw()，而不是假设所有接口都返回 JSON 对象。当前 apiFetch 也不会将后端 Set-Cookie 自动写入面向浏览器的响应，不能依靠它完成隐式会话刷新。

调试难点与可复用经验

工作台显示未登录时，先确认失败的是浏览器请求还是服务端请求，再看对应的 Cookie 是否到达后端；内部连接失败时，确认 Web 进程所在环境能解析目标地址；上传失败时，检查 FormData 和 Content-Type 是否匹配；数据没有更新时，再分别检查请求工具、页面和代理缓存。

这种定位顺序来自模块边界：浏览器负责对外请求，Web 负责同源转发或服务端聚合，后端负责身份与业务。把错误放回具体一段链路，比反复修改全部地址更容易找到原因。

今天的核对包括历史 diff、当前请求工具、rewrite 配置、工作台页面和客户端调用点；没有修改应用代码、启动应用服务或发起真实用户操作。本文没有把源码检查当成登录、上传或长连接的端到端验收，也没有调用游戏生成模型。

结论

两条请求路径共同支撑了游戏平台的页面读取和交互操作。稳定的基础是明确发起位置、目标地址、会话传递、编码、缓存和错误语义。后续无论游戏生成流程怎样变化，这些约定都应保持清晰，并通过真实部署环境中的请求验证它们。
