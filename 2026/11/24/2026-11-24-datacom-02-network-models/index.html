数通02：网络参考模型

发表于2026-11-24|更新于2026-11-25|数通基础
|总字数:5.3k|阅读时长:16分钟|浏览量:|评论数:

接着上一篇的办公室情景：电脑接入网络后，你打开浏览器，准备下载一份文件。

你看到的是网页和下载按钮，电脑要做的事却不止这些。浏览器要说明想要哪个文件，操作系统要把数据交给正确的连接，路由器要找下一跳，网卡还要把比特变成能在线路上传送的信号。

这些工作怎样配合？**网络参考模型就是把通信拆成几层，让我们知道每一层负责什么。**学它不是为了只背七个名字，而是为了看懂一次访问，以及出问题时先查哪一部分。

说明：本文用 HTTP / TCP / IPv4 / Ethernet 串起过程。实际网页还可能使用 DNS、TLS 或基于 QUIC 的 HTTP/3，不能把这个例子套到所有访问上。后面的抓包是自行搭建的实验步骤和预期，还没有在真机上实测。

信息传递过程

信息怎样变成数据

我们想传的是文字、图片、声音。应用会先按照约定，把这些内容变成计算机能保存和处理的数据。例如一段文字需要编码，一张图片有自己的文件格式；接收方也得按相同规则，才能把数据还原成有意义的内容。

所以，“把信息变成数据”并不是网线独自完成的。应用负责组织内容，协议栈逐步加入传输所需的信息，物理接口最后通过信号把比特送出去。接收端再按规则处理收到的数据，交给应用显示。

为什么要分层

假设浏览器既要处理网页，又要决定每种网卡的信号怎样发送，那么换一块网卡，就可能牵动整个应用。分层把这些工作拆开：上层使用下层提供的能力，下层不必理解文件里写了什么。

以下载文件为例，应用关心请求和响应，传输层关心端到端的数据传送，网络层关心去往哪个网络，链路层关心当前这一段交给谁，物理层则负责比特传输。

**同层按协议约定通信，相邻层在本机里配合。**图上常画“客户端应用层对服务器应用层”，那是逻辑上的对应关系；数据真正离开电脑时，仍然要先沿着协议栈向下走，再经网络到达对方。

常见模型放在一起看

常见的有 OSI 七层、TCP/IP 四层，以及学习中常用的五层表示法。图 1 展示了大致对应关系。

图 1 三种网络参考模型

层数不同，不是三套网络各干各的，而是观察和划分职责的方式不同。先知道自己用哪种模型，再谈“第几层”，就不会把四层里的网络接口层和五层里的物理层混在一起。

OSI 七层模型

七层分别负责什么

从上往下依次是：应用、表示、会话、传输、网络、数据链路、物理。不要只背顺序，还要能举出每层在处理什么。

表 1 OSI 七层的作用

层次 主要工作 放到访问网页里理解
应用层 提供应用使用的网络协议 HTTP 表达请求哪个资源、返回什么内容
表示层 处理编码、格式、压缩和加密等表示问题 双方需要看懂交换的数据格式
会话层 建立、管理和结束会话 从模型上理解交互怎样组织和维持
传输层 为通信端点提供传输服务 TCP 提供可靠、有序的字节流
网络层 逻辑寻址与跨网络转发 依据 IP 和路由选择下一跳
数据链路层 成帧、链路寻址和差错检测等 把以太网帧交给当前链路上的下一站
物理层 通过介质传送比特 用电、光或无线信号承载比特

七层是理解职责的框架，不要求每个软件真的有七个独立模块。尤其是上三层，在 TCP/IP 应用里往往由应用和相关库一起承担。

注：应用层不是浏览器窗口本身，而是应用使用的网络协议功能。网站登录状态、TCP 连接与 OSI 会话层也不能直接画等号，要看具体实现承担了哪些工作。

传输层一定可靠吗

**不能把“传输层”直接等同于“可靠传输”。**TCP 提供确认、重传、有序交付等机制；UDP 不提供 TCP 式的可靠字节流保证。应用选了 UDP，又希望可靠传输，就需要相应的上层机制。

同样，链路层有差错检测，也不代表所有链路协议都会自动重传并保证最终送达。看模型时先记职责，再看具体协议提供了什么服务。

TCP/IP 模型

四层怎样划分

TCP/IP 四层从上到下是：应用层、传输层、网际层、网络接口层。网际层在很多入门说明中也称网络层。

应用层承接 HTTP、DNS 等应用协议；传输层常见 TCP、UDP；网际层以 IP 为核心，处理跨网络寻址和转发；网络接口层负责通过具体链路收发数据。

RFC 1122按链路层、IP 层和传输层讨论主机的通信要求，应用层由配套规范讨论。这里把四层作为理解 TCP/IP 协议体系的常见框架，不把它说成“实际设备必须恰好分成四块”。

五层为什么多一层

五层把底部拆成数据链路层和物理层，顺序变成：应用、传输、网络、数据链路、物理。这样既能单独讲以太网帧，也能单独讲接口、网线与信号，更方便学习。

不是网络多了一次发送，也不是四层模型缺了一块能力，只是把原来放在网络接口层讨论的工作分开看。

表 2 五层职责与常见例子

层次 主要问题 常见例子
应用层 要提供什么业务、数据怎样表达 HTTP、DNS、DHCP、SMTP
传输层 两端的数据交给哪个通信端点 TCP、UDP、端口
网络层 目的地在哪个网络、下一跳是谁 IP、ICMP、路由
数据链路层 当前链路怎样交付一帧 Ethernet、PPP、MAC 地址
物理层 比特怎样通过介质传递 接口、线缆、电光信号

端口、IP 和 MAC 为什么都需要

这三个标识不是重复填写的“地址”。端口帮助区分传输端点，IP 用来进行网络层寻址，MAC 用于以太网当前链路上的交付。

例如电脑访问另一个网段的服务器：目的 IP 指向服务器，目的 TCP 端口指向服务器上的服务，而首跳帧的目的 MAC 指向网关接口。电脑先把帧交给网关，不是直接把一份以太网帧扔到远端服务器。

数据封装和解封装

发送端怎样逐层封装

假设电脑已经知道服务器的 IPv4 地址，这次访问使用 TCP。图 2 把发送端的处理从上到下排开，也标出了接收端相反的处理方向。

图 2 封装与解封装的方向

一份请求怎样离开电脑

应用层：准备请求

HTTP 写清要访问哪个资源。应用数据本身也有格式，并不是到了下面才第一次被组织。

传输层：加入 TCP 头

TCP 把字节流组织为报文段，加入源端口、目的端口、序列号等信息。TCP 不保留应用消息边界，一条 HTTP 消息可以分布在多个 TCP 段中。

网络层：加入 IP 头

IP 包携带源、目的 IP 等信息，TCP 段成为它的载荷。网络层据此处理寻址与转发。

数据链路层：组织当前链路的帧

以太网加入相应头部和 FCS 等信息，目的 MAC 对应这段链路上的接收方。访问远端网段时，电脑先交给网关。

物理层：发出信号

网卡通过介质传送比特。物理层不是再给数据套一个“物理层头”。

“载荷”可以理解为这一层承载的内容。TCP 头和应用数据放在一起，是 IP 层的载荷；IP 头和它的内容，又一起放进以太网帧。同一段内容，换一层看，角色也跟着变。

注：图中块的宽度不代表实际字段长度，也不表示一条应用消息总能放进一个帧。这里用 TCP 举例；使用 UDP 时应叫 UDP 数据报，不能把所有传输层数据都叫 TCP 段。

交换机和路由器做什么

数据经过中间设备，不等于每台设备都把文件交给自己的应用打开一次。

表 3 普通转发路径中的设备分工

设备 在这条路径中主要做什么
普通二层交换机 根据 VLAN、目的 MAC 等二层信息转发帧
路由器 处理入站链路封装，检查 IP 包，选下一跳，再按出站链路重新封装
目标主机 沿协议栈向上处理，将数据交给对应的应用

在普通 IPv4 路由转发中，路由器会递减 TTL，并更新 IPv4 首部校验和；没有 NAT、隧道等额外处理时，源、目的 IP 通常保持不变。当前链路的 MAC 与封装则会随下一段连接重新构建。

**IP 指向最终目的地，链路帧负责这一段交给谁。**所以经过路由器后，不能期待两边抓到完全相同的以太网头。

接收端怎样解封装

服务器收到发给自己的帧，先检查相应链路信息，再把 IP 包交给网络层处理。接着由 TCP 等协议处理传输信息，把数据交给监听相应端口的应用。

这里不只是“每层撕一张纸”。TCP 还要处理顺序、重传和重组，应用还要解释自己的消息格式。只有相关处理完成，浏览器才能显示文件或页面。

抓一次请求，再分层展开

  1. 在客户端网卡开启 Wireshark，对应图中的抓包点 A；有条件时也在服务器网卡开启抓包点 B。
  2. 访问自己的测试地址 http://198.51.100.20:8000/，或请求该服务上一张不含敏感内容的测试图片。
  3. 停止捕获，先按客户端 IP 或 TCP8000 找到这次连接，再挑选带有应用数据的报文展开。
  4. 依次观察 Ethernet、IPv4、TCP、HTTP，记录源与目的 MAC、IP、端口和请求内容。如果 TCP8000 的明文 HTTP 未被自动识别，可通过 Analyze → Decode As 把该会话交给 HTTP 解析器；这只是指定解析方式，不会解密加密流量。
  5. 若两侧都有抓包，比较跨路由转发前后的 IP、TTL、链路地址。比较时匹配同方向、同一连接的对应报文，不随意挑两条记录。

客户端的源端口通常由操作系统选择，不要事先把它写死成80或8000；服务器监听端口在这个实验里才是8000。回复时两端的源、目的端口会交换方向。

注：在客户端网卡抓包，通常看不到路由器另一侧的链路帧。图中的两个观察点是为了比较不同链路，不代表单台电脑能自动看见交换机所有端口。网卡卸载也可能影响校验和和分段的显示，应结合观察位置解释。

按 IP、MAC、端口和协议筛选

下面都填在顶部的显示过滤器里，用于筛选已经捕获的数据。示例 MAC 要替换成实际网卡地址，不要把它当成图中设备必然具有的地址。

ip.addr 匹配源或目的地址，适合看双向通信；ip.src 和 ip.dst 则分别限制方向。只看去程时，可以同时指定源和目的。

第一条匹配以太网源或目的 MAC，第二条只匹配源 MAC。MAC 的判断要配合抓包点：服务器一侧看到的帧，不会沿用客户端发给首跳网关的全部链路地址。

三条是独立条件。8000用于本次测试；443的例子分别找TCP或UDP上的对应端口。端口号是线索，不能只凭443就断言当前报文一定是什么应用。

http、dns、arp 找被解析为对应协议的记录；and 组合条件。最后一条排除源或目的为该IP的记录，括号让要排除的范围更清楚。

这些字段和语法可对照 Wireshark 显示过滤器说明。显示过滤只改变当前看哪些包，不会把其他已经抓到的记录从文件里删掉。

显示过滤与捕获过滤别混用

显示过滤是在抓到数据后筛选，捕获过滤则在捕获时决定留下哪些流量，两者语法不同。例如显示过滤写 ip.addr == 192.0.2.10，捕获过滤通常用 host 192.0.2.10 这样的表达。不要把前一条原样填进捕获过滤框。

第一次练习可以先用显示过滤。过早把捕获条件设得太窄，可能连排查所需的 ARP、DNS 或回程流量都没留住，后面就无从对照。

图片数据怎样观察

用自己的测试图片发送请求，再看 HTTP 响应的类型和内容，比随机抓一段流量更容易理解“应用内容被拆成报文传输”。图片通常跨多个 TCP 段，不能指望随便点开一个包就看到整张图。

对于捕获完整、能被正确解析的 HTTP 对象，可尝试 Wireshark 的 HTTP 对象导出功能。协议和对象导出说明可查 Wireshark 用户指南。这属于解析、重组后的结果，不是额外增加了一层网络协议。

抓到了聊天软件发图片的流量，就能直接导出原图吗？

**不能仅凭抓到了流量就保证还原图片。**还要看实际传输协议、是否加密、捕获是否完整，以及解析器能否识别和重组对象。加密内容没有相应解密条件时，看到包长、地址和时间，也不等于看到了图片明文。

如果用 QQ 等聊天软件做自己的图片传输练习，可以先记录时间、地址、连接与流量变化；无法导出图片时，不能直接判断发送失败。刚开始学习，先用可控的明文 HTTP 测试服务把封装与重组看清，再研究具体应用协议。

重点回顾

把一次访问串起来

先记住这条线：应用准备请求，传输层处理端到端传送，网络层处理寻址和转发，链路层组织当前链路的帧，物理层传送比特。接收端按相反方向逐层处理，最后把数据交给应用。

再分清三组概念：四层和五层是不同划分；端口、IP、MAC 解决不同范围的问题；抓到数据包与看懂应用内容也不是一回事。把这些区别放回刚才的拓扑，比单背层名更容易记住。

面试问题

网络通信常参考哪些模型，分别有几层？

**常见有 OSI 七层、TCP/IP 四层，以及学习中常用的 TCP/IP 五层表示法。**OSI从上到下是应用、表示、会话、传输、网络、数据链路、物理；TCP/IP四层是应用、传输、网际、网络接口；五层再把底部拆成数据链路与物理。

回答“网络有几层”之前先说模型。否则一个人说物理层是第一层，另一个人用四层框架讨论网络接口层，听起来就像在互相纠错。

TCP/IP 分几层，每层做什么？

**按四层说，应用层处理应用协议，传输层提供通信端点间的传输服务，网际层负责 IP 寻址与转发，网络接口层负责通过具体链路收发。**按五层说，再把底部拆成成帧与链路交付、比特传输两部分。

例如HTTP、TCP、IPv4、Ethernet与物理信号，分别帮助解释五层职责。但传输层不只TCP，也不能说所有传输层协议都保证可靠。

数据怎样封装和解封装？

**发送端向下处理，在相应层加入本层信息；接收端向上处理，再把载荷交给上一层。**本例先组织HTTP数据，再加入TCP头、IP头和以太网封装，最终以信号发送。服务器收到后逐层检查，TCP处理重组与有序交付，应用再解释HTTP内容。

中间路由器不需要把文件交给自己的HTTP应用打开。它处理网络层和两侧链路封装；普通二层交换机则主要按二层信息转发。

Wireshark 怎样过滤 MAC、IP、端口和协议？

**显示过滤可用 eth.addr == 地址、ip.addr == 地址、tcp.port == 端口，以及 http、dns 等协议名。**要限定方向，就选 eth.src、ip.dst 等方向字段；要同时满足条件，用 and，任一满足用 or，排除用 not (...)。

例如本次实验看客户端的TCP8000通信，可写 ip.addr == 192.0.2.10 and tcp.port == 8000。这些是显示过滤表达式，不是发到设备上的配置命令，也不能原样充当捕获过滤器。

其他常见问题

跨网段访问时，第一帧的目的 MAC 是服务器的吗？

**在图3的以太网实验里，不是，是所选网关接口的 MAC。**目的IP仍是服务器 198.51.100.20，但电脑先把帧交给 192.0.2.1 对应的网关。R1再为通向服务器的那段链路重新封装。

二层交换机就绝对不会处理三层信息吗？

**不能用“二层”把设备的全部能力锁死。**这里描述的是普通二层转发路径，实际设备还可能支持三层交换、访问控制或管理IP。分析某份报文时，要看当前启用的功能和它走的路径，不只看设备名称。

HTTPS 抓包为什么看不到明文 HTTP？

**因为应用数据受加密保护，抓到TLS等流量不等于已经解密。**没有相应解密条件时，http 过滤为空也不能说明没有发生网页访问。先确认实际使用TCP还是QUIC等传输路径，再看捕获位置与解密条件。
