数通09：传输层

发表于2026-11-27|更新于2026-11-27|数通基础
|总字数:6.5k|阅读时长:20分钟|浏览量:|评论数:

网关和路由把数据送到目标主机之后，主机还要知道：这份数据交给浏览器、文件服务，还是其他应用？传输层通过端口等信息区分通信端点，再由具体协议提供相应的传输服务。

这一篇按传输层作用、TCP工作原理、UDP工作原理展开。应用端口表保留原有行列，重点回顾保留五道问题的顺序和问法；容易误解的端口、标志位和窗口问题，在对应位置单独说明。

说明：文中的序号、窗口和报文是过程示例，不是实测抓包输出。配图为依据协议过程制作的示意图；本篇没有独立的设备配置实验，不另外添加一套路由器配置来替代协议讲解。

传输层的作用

从主机交付到通信端点

在TCP/IP五层模型中，从物理层往上数，传输层是第四层，位于网络层与应用层之间。它接收应用数据，加入传输层首部，帮助操作系统把收到的数据交给正确的通信端点，也就是完成复用与分用。

TCP、UDP、SCTP都是传输层协议。TCP提供可靠、有序的字节流；UDP提供无连接的数据报服务，不在协议本身实现确认和重传；SCTP也支持可靠传输，常见于信令等场景。

**可靠性和流量控制是具体协议的能力，不能说所有传输层协议都保证正确送达。**UDP应用需要这些能力时，可以在上层自行实现，而不是因为用了UDP就完全不关心数据是否到达。

TCP与UDP报文格式

先把字段放在一起看。TCP不带选项时首部为20字节，包含选项时可以更长，最大60字节；UDP首部固定8字节。首部长度不是整个报文长度，后面还承载应用数据。

图 1 TCP与UDP报文格式

这张图沿用经典TCP布局，Control bits (6)专门列出六个传统标志位，Reserved (6)是当时的保留位布局。它适合讲基本字段，但不代表后续标准没有扩展。表1按RFC 9293基础格式列出保留位与扩展标志，二者要放在各自版本背景里理解。

从图的上方向下读，第一行源、目的端口各16位，合起来32位；下面Seq与Ack各占一整行32位。TCP部分每整行宽度代表32位，也就是4字节，不是看框在屏幕上多宽就代表多少字节。

基本首部从端口到Urgent Pointer共20字节，Options不算在固定20字节里。Header Length记录包含选项和填充后的实际首部长度，单位是4字节；因此值5对应20字节，值8对应32字节。Data不是首部字段，它是TCP承载的上层字节。

UDP只有两行首部：端口占4字节，Length与Checksum再占4字节，总计8字节。它没有TCP的Seq、Ack、Window或控制位，所以不能要求UDP首部自己完成TCP式握手、按序确认与窗口调节。

表 1 TCP首部主要字段

字段 长度 作用
Source Port 16 bit 源端口
Destination Port 16 bit 目的端口
Sequence Number 32 bit 字节流序号；携带数据时指向该段首个数据字节，SYN另占一个序号
Acknowledgment Number 32 bit ACK置位时表示下一个期望收到的序号
Data Offset / Header Length 4 bit 首部长度，以4字节为单位；值5表示20字节
Reserved RFC 9293基础格式为4 bit 保留字段，不能继续把旧布局当成所有现行格式
Control Bits RFC 9293基础格式列8个标志 CWR、ECE、URG、ACK、PSH、RST、SYN、FIN
Window 16 bit 本方向通告给对端的接收窗口；实际解释还需考虑窗口扩大选项
Checksum 16 bit 对TCP首部、数据及伪首部相关信息进行校验
Urgent Pointer 16 bit URG有效时配合序号指示紧急数据边界
Options与Padding 可变 选项与填充，首部保持4字节对齐

经典简图里常把“保留6位、控制6位”放在一起，便于认识SYN、ACK、FIN等基本标志；当前基础格式可对照 RFC 9293。TCP最早由RFC 793定义，RFC 9293已整合更新其基础规范。这里重点看每个字段做什么，不照抄过时位宽。

表 2 UDP首部字段

字段 长度 作用
Source Port 16 bit 源端口
Destination Port 16 bit 目的端口
Length 16 bit UDP首部与数据的总长度，至少8字节
Checksum 16 bit UDP校验字段，不能把它理解成确认或自动重传

UDP载荷位于这8字节首部之后。字段定义见 RFC 768。UDP按数据报交付，保留消息边界；TCP交付字节流，应用写入一次不意味着对端一定只读一次就收到相同边界。

Control bits：六个经典控制位

图中6 bit不是一个“取值0到63的状态编号”，而是六个独立开关。从经典图的高位到低位依次是 URG、ACK、PSH、RST、SYN、FIN，每个标志各占1 bit。同一个报文可以把多个开关同时置1，所以SYN+ACK和FIN+ACK都很常见。

只看这六位时，对应掩码分别为 0x20、0x10、0x08、0x04、0x02、0x01。例如SYN+ACK为 0x12，FIN+ACK为 0x11。扩展标志存在时，整个标志字段还可能包含其他位，不能把这组经典掩码当成所有扩展的完整定义。

SYN：同步序号，建立连接

SYN用于建立连接时同步初始序号。客户端先发SYN，服务器以SYN+ACK应答，其中SYN表达服务器自己的序号起点，ACK确认客户端的起点。第三次回复只有ACK，不需要再次发SYN。

SYN本身占用一个序号，因此收到 seq=a 的SYN后，应确认 ack=a+1。抓包时若看到多次同方向SYN、相同序号，却没有应答，要继续查目标监听、链路或策略；单靠重复SYN不能直接断言“服务器宕机”。

ACK：确认号字段有效

ACK置1表示首部中的Acknowledgment Number有效，说明接收方下一步期望收到哪个序号。比如 ack=1501 表示在对应连接的序号关系中，接收方已经连续接收到序号1500（含）为止的相关字节，下一步期待1501，而不是“刚收到了第1501个报文”。

连接建立后，很多携带数据的段也会置ACK，因为TCP可以在发送本方向数据的同时确认反方向数据。ACK段不一定是一个只有确认、没有载荷的空包；纯ACK本身不推进发送序号。确认到达TCP接收端，也不代表对方应用已经读走、保存或成功处理了数据。

FIN：结束一个发送方向

FIN表示发送方后面不再发送新的普通数据，用于正常关闭自己的发送方向。它也消耗一个序号，所以对端确认FIN时，确认值相应加1。

A发FIN、B回ACK，只说明A→B这个发送方向正在关闭，B仍可以继续把剩余数据发给A。等B也发FIN、A确认，两个方向才完成相应关闭步骤。不能把FIN理解成一按就瞬间把整条双向连接清空。

RST：重置连接

RST用于拒绝或中止不适当的连接状态，与FIN的有序关闭不同。例如目标没有对应监听服务时，设备可能对到达的SYN返回RST；已建立连接也可能因异常被重置。

RST不走正常FIN逐方向关闭的过程，也不保证尚未交付的数据会被对端应用处理。抓到RST时，要看它由谁发出、之前是什么报文、序号与确认关系是否合理；不能仅凭RST就认定一定是服务器主动故障，路径上的策略设备也可能参与响应。

PSH：请求及时向接收应用交付

PSH表达推送语义，希望接收端及时将相应数据交给应用，而不是为了等待更多数据而继续积攒。实际表现受TCP实现和应用读取方式影响，不能把它当成确定的时延保证。

PSH不增加传输优先级，不代表紧急数据，也不提供应用消息边界。看到PSH+ACK，只能结合载荷说明这段数据带有推送与确认标志，不能据此断言“恰好是一条完整HTTP消息”。应用仍需按自己的协议格式解析字节流。

URG：紧急指针有效

URG置1表示Urgent Pointer需要参与解释。紧急指针与序号一起标识紧急数据的边界，具体边界语义还需考虑协议规范及实现差异，不是把整段报文都变成一条高优先级通道。

URG与PSH是两回事：前者关联紧急指针，后者关联推送语义。它们都不保证报文能在网络中插队。普通HTTP传输通常不需要应用依赖这套紧急数据机制，排查时也不要把图中的Urgent字段误看成端口号或普通载荷长度。

把标志组合放回通信过程

建立阶段常见SYN、SYN+ACK、ACK；传输阶段常见ACK以及PSH+ACK等组合；正常关闭常见FIN+ACK与ACK；异常中止则可能出现RST或RST+ACK。这些是常见过程，不是“一种标志只允许出现在唯一阶段”的死规定。

读包时先明确连接和方向，再同时看Flags、Seq、Ack、载荷长度与Window。例如一个带数据的ACK段，可以既交付本方向数据，又确认反方向字节；这些字段配合起来才构成完整含义。

端口号的作用与范围

TCP和UDP的源、目的端口都是16 bit，编码范围0—65535，共65536种取值。端口0有保留含义，不应当作普通服务端口使用。TCP端口和UDP端口属于不同协议空间，不能把它们混成同一个监听项。

客户端发起连接时，源端口通常由操作系统从临时端口范围选择；实际范围取决于系统配置，不能规定所有系统都固定从1024开始随机分配。服务端则在指定端口监听，客户端把它填写为请求的目的端口。

比如主机A的临时端口为1027，访问HTTP服务器80端口：请求是 1027 → 80，响应则是 80 → 1027。源端口并不永远是客户端端口，目的端口也不永远是服务器端口，它们随报文方向变化。

区分一条TCP连接通常还要看源IP、源端口、目的IP、目的端口，并明确传输协议。单看“目的端口80”，不能区分所有正在访问这个服务的客户端。

TCP工作原理

基本概述与常见应用

TCP是面向连接、提供可靠有序字节流的传输层协议。它通过序号、确认、重传等机制处理丢失与乱序，并通过窗口等机制协调发送。可靠字节流不等于连接永不失败，也不保证对方应用已经完成保存或业务处理。

下面保留常见TCP应用表的协议顺序与端口写法，默认值和部署替代端口在表后区分。

表 3 常见的TCP应用

协议 端口号
FTP 21、20
HTTPS 443、8443
HTTP 80、8080
Telnet 23
SSH 22
SMTP 25

注：HTTP默认80，HTTPS默认443；8080是常用HTTP替代端口，8443常见于HTTPS服务的替代部署，不能把它们都叫标准默认值。HTTPS默认8080的说法不正确，可核对 IANA端口登记。FTP的21用于控制连接，20常用于传统主动模式的数据连接；被动模式的数据连接通常使用服务端协商的其他端口，不是所有FTP数据都固定走20。

建立连接：三次握手

普通TCP连接先同步两端的初始序号，再进入已建立状态。图2用a、b分别表示两端初始序号，按时间从上到下看。

图 2 TCP三次握手

  1. 主机A发送SYN，seq=a，提出建立连接并通告自己的初始序号。此时ACK未置位，不能把确认字段中的数字当作有效确认。
  2. 服务器回复SYN+ACK，seq=b，ack=a+1，确认收到A的SYN，同时通告自己的初始序号。
  3. A发送ACK，seq=a+1，ack=b+1，确认服务器的SYN。第三步是ACK，不是再发一个SYN。

SYN会消耗一个序号，所以双方确认值都要加1；不带数据的普通ACK本身不消耗序号。经过这三个方向的交换，双方各自的发送序号才能被对端确认。第三步也可以携带数据，不能据简化图断言“所有应用字节都必定出现在第四个包”。

观察握手时，先定位同一连接，再看SYN/ACK标志和两个方向的Seq、Ack。分析器常默认显示相对序号，把a、b显示为0，这是显示方式，不是说真实初始序号都为0。

关闭连接：四次挥手

TCP是全双工，两个发送方向分别关闭。图3采用A主动关闭、服务器此后没有额外发送数据的简化情形，u、v表示关闭时双方下一个待发送序号，不是直接沿用握手初值。

图 3 TCP关闭连接

表 4 正常关闭的四个步骤

步骤 方向 标志与序号 含义
一 A→服务器 FIN+ACK，seq=u，ack=v A不再发送新数据，请求关闭自己的发送方向
二 服务器→A ACK，seq=v，ack=u+1 确认A的FIN；服务器仍可继续发数据
三 服务器→A FIN+ACK，seq=v，ack=u+1 服务器也结束发送；本例中间没有额外数据
四 A→服务器 ACK，seq=u+1，ack=v+1 确认服务器FIN；主动关闭方进入TIME_WAIT

FIN和SYN一样占用一个序号。若服务器在第二、三步之间还发了数据，它的后续序号会推进，不能机械套用表里的v。A发出FIN并不等于“从此完全不能接收服务器数据”，这是半关闭的含义。

服务器对FIN的ACK与自己的FIN可以合并，所以正常关闭不保证抓到恰好四个独立包；异常重置也不是四次挥手。TIME_WAIT用于处理最后ACK丢失后的FIN重传及旧报文等问题，不是发出最后ACK就立即释放所有状态。

传输过程：序号、确认与重传

下面保留一组连续数据段的编号和字节范围。假设每段携带500字节，从M开始发送，N+3丢失。

图 4 TCP累计确认与重传

先看上方三段，每段500字节，总计连续收到1500字节，因此服务器向左确认M+1500。接着N+3的红色叉号表示这段没有到达；即使后面更大序号的数据先到了，中间缺口也仍然存在，所以第二个向左箭头的确认号不前进。

下方再次出现相同的字节范围，表示重发原来的字节，不是重新给同一份数据分配另一组序号。图4沿用一种简化的连续重传示意，假定后续段没有被保留；实际实现若已缓存后续数据，未必需要把后三段全部重发。末尾M+3000的确认，以这三段都补齐、前3000字节连续接收为前提。

表 5 六个数据段的字节序号

数据段 数据字节范围 接收情况示例
N M—M+499 收到
N+1 M+500—M+999 收到
N+2 M+1000—M+1499 收到
N+3 M+1500—M+1999 丢失，需要补齐
N+4 M+2000—M+2499 可能先于缺失段到达，形成乱序
N+5 M+2500—M+2999 同上

接收端已经连续收到M到M+1499，累计确认就是 ack=M+1500，表示下一个期望字节。后面的N+4、N+5即使到了，也不能抹去中间的缺口，因此累计确认可以继续停在M+1500。

发送端根据确认、超时和相应丢失检测机制决定重传。**确认号不前进，不等于接收端完全没有收到后面的任何数据。**启用SACK时还可以报告已收到的非连续范围；后续段可能被缓存，所以不能规定N+3丢失后一定把N+4、N+5全部重发。

若缺失段补齐，且N+4、N+5仍在缓存，累计确认就可以推进到M+3000。判断重传时，要比较同一方向的序号范围、确认和上下文；同一个Seq再次出现是线索，不能脱离抓包位置、重复采集等条件直接给出故障结论。

流量控制：滑动窗口

图5保留1024字节分段、4096与3072窗口，以及3073、6145两个确认号，调整为能连续对应的收发过程。接收端持续有应用读取数据，不能一边说缓存完全满，一边又通告3072字节可用空间。

图 5 TCP接收窗口与字节推进

从最上方服务器向左的ACK看起：ACK=1，Window=4096 表示从序号1起允许接收4096字节。客户端这一轮只先发送三段，每段1024字节，序号分别是1、1025、2049。窗口是上限，不要求发送方每轮必须填满四段。

连续收到前三段后，服务器确认3073。如果初始接收空间4096、这时应用已读走2048字节，那么剩余可用空间为 4096−3072+2048=3072，因此通告Window3072是合理的。它允许从3073起再收3072字节，即到6144。

下一轮三段从3073、4097、5121开始，全部连续收到后才确认6145。如果应用继续读取，服务器仍可以通告3072，接下来的三个起点便是6145、7169、8193。图中Window只标在服务器返回的确认上，用来表达服务器的接收能力；前向数据段自己的Window字段通告的是另一方向的接收能力，不能拿来替代它。

流量控制主要解决“接收方来不来得及收”。接收方通过自己发出的TCP首部Window字段，告诉对端当前愿意接收多少数据；它通告的是自己的接收能力，不是要求自己接下来发多少。发送方还受拥塞控制等约束，不能把发送上限只理解成一个Window数。

用1024字节数据段举例，先忽略窗口扩大：如果接收方从序号1开始允许4096字节，那么这个窗口覆盖1—4096。发送方可在该范围内有多个尚未确认的数据段，不需要每发一段都停下来等待。

当接收方连续收到了前三段，也就是1—3072，确认号为3073。若这时通告窗口3072，含义是从3073开始还允许3072字节，右边界到6144；ACK确认的是已连续收到哪里，Window说明的是后面还能接多少，这是两件事。

注：如果接收缓存真的已经没有可用空间，应通告零窗口，而不是同时说“缓存满了”却又声称还能接收3072字节。ACK6145只有在前6144字节连续接收后才成立；中间1024字节段丢失时，后续确认不能直接跳过缺口。上述数字用于分别解释窗口与累计确认，不应拼成一条自相矛盾的实测记录。

接收应用读走数据后，可用空间增加，窗口可以更新。出现零窗口时，发送方应遵守接收方限制，并通过相应探测机制了解窗口是否恢复。抓包分析慢传输时，区分接收窗口受限、网络丢包和拥塞，不能看到吞吐低就一律解释成“接收缓存满”。

UDP工作原理

基本概述与常见应用

UDP是无连接的数据报传输协议，发送前不需要TCP式三次握手，也不维护TCP式序号确认和重传状态。它开销小，适合由应用自行权衡时延、消息边界与可靠性的场景，但不承诺一定比TCP更快、一定不丢包。

表 6 常见的UDP应用

协议 端口号
DNS 53
NTP 123
TFTP 69
SNMP 161

注：DNS也使用TCP53，不能说DNS只走UDP。TFTP的69常用于初始请求，后续传输使用协商出的传输标识端口；SNMP161常用于查询与代理服务，通知还常涉及162。这里保留应用表的四行，不把它扩写成“每个应用永远只使用这一个UDP端口”。

UDP传输过程

应用交给UDP一份数据，UDP加上8字节首部，再交给IP发送。接收方依据目的端口分用到相应端点；UDP本身不会因为没收到应用响应就自动重发，也不会替应用把多份乱序到达的数据报排好。

如果业务需要到达确认、排序、重传或流量控制，由上层按需提供。语音、视频等时延敏感流量经常采用UDP，但应用可能有自己的恢复与拥塞处理，不能把“用UDP”翻译成“业务不需要可靠性”。网络路径如何选择仍由IP路由等机制决定，也不是UDP主动选多条路线。

重点回顾

面试问题

传输层的作用是什么

传输层位于应用层和网络层之间，主要为通信端点提供传输服务，并通过端口等信息把不同应用的数据区分开。网络层负责把IP包送向目标主机，传输层进一步帮助主机确定数据交给哪个通信端点。

不同协议提供的服务不同。TCP提供可靠、有序的字节流，并有确认、重传和流量控制；UDP提供无连接的数据报服务，不自带TCP式可靠传输。比如浏览器访问HTTP服务时，服务端通常监听固定端口，而客户端使用本机的临时端口参与这次通信。

TCP和UDP的区别是什么

TCP是面向连接的可靠字节流协议，通常先握手，传输中通过序号、确认和重传处理丢失与乱序，还提供流量控制和拥塞控制。UDP是无连接的数据报协议，保留消息边界，不在协议本身做这些TCP式的确认、排序和重传，固定首部也更短，只有8字节，TCP基本首部至少20字节。

选择时我会看业务需要什么，而不是简单说UDP一定更快。比如文件内容需要完整、有序地交给应用，TCP能直接提供相应基础；实时语音可能更重视及时播放，可以使用UDP并由上层选择丢失处理方式。业务如果在UDP上实现可靠机制，仍可能是可靠应用，只是能力不由UDP自身提供。

讲述TCP三次握手的过程

以客户端主动连接服务器为例，第一次客户端发SYN，序号为a。第二次服务器回复SYN加ACK，序号为b，确认号为a+1，既确认客户端的SYN，也通告自己的初始序号。第三次客户端回复ACK，序号为a+1，确认号为b+1，确认服务器的SYN。SYN会占一个序号，所以双方确认时都加1。

这三步完成双向序号同步。第三步应当是ACK，不是再发一次SYN；如果抓包显示0和1，还要确认工具是否启用了相对序号显示，不能以为真实初始序号都固定为0。

IP的端口有多少个，其作用是什么

准确地说，端口是TCP、UDP等传输层协议的字段，不是IP首部里的字段。TCP和UDP的端口号都是16位，范围0到65535，各自有65536种编码，其中0是保留值。端口帮助操作系统区分通信端点，让到达同一台主机的不同业务交给正确的应用。

例如一个客户端从本机1027端口访问服务器80端口，请求的源、目的端口分别是1027和80，回复时交换方向。区分具体连接还要结合双方IP与端口，并明确使用哪个传输协议，不能只看一个端口就认定是同一条会话。

FTP、Telnet、SSH、HTTP、DNS、SNMP的传输端口号是多少

FTP控制连接通常使用TCP21，传统主动模式的数据连接常涉及TCP20；被动模式则使用服务端协商的其他数据端口。Telnet通常用TCP23，SSH用TCP22，HTTP默认TCP80，8080是常见替代部署。DNS使用53端口，同时支持UDP和TCP。SNMP查询、代理服务常用UDP161，通知还常用UDP162。

这些是常见约定，实际服务可以更换监听端口。排查时我会把协议类型与端口一起确认，再看进程和抓包，不会仅凭“用了80”就断言报文一定是明文HTTP。完整的TCP与UDP应用清单仍见表3、表6，包含HTTPS、SMTP、NTP和TFTP。
