AI 游戏平台何时就绪？从 API 探针到 Worker 心跳

发表于2026-11-06|更新于2026-11-07|AI 3D 游戏生成
|总字数:1.1k|阅读时长:3分钟|浏览量:|评论数:

游戏生成请求依赖后台 Worker。API 即使已经监听端口，用户提交的任务也需要有人接手。这个项目用一个就绪探针串起数据库、存储和 Worker 心跳，Compose 再根据探针结果启动 Web。

本文对照了 2026 年 8 月 3 日提交 fabfabfb 和当前工作区。两处的健康控制器实现一致。下面的启动依赖取自当前 docker-compose.yml，Worker 定时器取自当前源码。

从基础依赖到站点入口

迁移任务等 PostgreSQL 健康，MinIO 初始化任务等 MinIO 健康。迁移和存储初始化完成后，API 可以启动。Agent 还要等 Runner 初始化完成，随后执行 LangGraph 初始化脚本，再进入 Worker 进程。

API 与 Agent 分别依赖这些初始化任务。Agent 的启动条件里没有 API 健康这一项，所以即使 API 正在等心跳，Agent 也能启动并写入心跳。Web 则明确等待 API 健康，网关等待 Web 和 API 都健康。

    flowchart TD
  P[PostgreSQL 健康] --> M[数据库迁移完成]
  S[MinIO 健康] --> I[存储初始化完成]
  M --> A[启动 API]
  I --> A
  M --> W[启动 Agent Worker]
  I --> W
  R[Runner 初始化完成] --> W
  W --> H[写入近期心跳]
  A --> K[探针检查数据库与存储]
  H --> K
  K -->|通过| V[启动 Web]
  K -->|通过| G[网关等待 API 与 Web]
  V -->|Web 健康| G

API 怎样判断就绪

实际接口为公开的 GET /api/v1/health。apps/backend/src/health/health.controller.ts 依次执行数据库查询、存储检查和心跳查询。数据库步骤运行 SELECT 1。存储步骤调用 StorageService.ready()，MinIO 分支执行桶准备，本地分支确保目录存在，其他分支取得当前存储适配器。不同分支覆盖的存储能力有差别，排查时要结合驱动看。

为什么启动顺序容易误判

Compose 中，service_completed_successfully 用于等待一次性任务成功退出，service_healthy 用于等待常驻服务通过健康检查。当前 API 容器内每 10 秒请求一次健康接口，单次探针超时 5 秒，配置 20 次重试。HTTP 非成功状态和请求失败都会让探针命令失败。API 监听端口与通过该探针可能发生在不同时间。

先看迁移与存储初始化是否完成，再检查 API 日志里的数据库或存储失败。若接口明确返回 Worker 尚未就绪，再检查 Agent 的 Runner 初始化、LangGraph 初始化和心跳写入。API 与 Worker 还要使用同一个数据库，否则 Worker 写入的记录对 API 不可见。这个排查顺序对应探针的执行次序，可以避免在数据库步骤尚未通过时优先追查心跳。

验证范围与结论

本次核对了历史控制器、当前 Worker、存储适配入口、Compose 依赖及项目架构文档。启动图来自这些源码与配置，本次未运行 Compose 或触发真实生成任务。

项目用就绪探针表达启动 Web 前需要哪些依赖达到可用状态。把一次性初始化、进程探测和 Worker 心跳分别建模后，启动阻塞可以沿依赖定位。任务级进展、队列积压和模型调用仍需在运行层单独观测。
