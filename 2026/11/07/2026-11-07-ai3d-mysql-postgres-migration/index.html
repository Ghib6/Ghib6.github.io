从 MySQL 到 PostgreSQL：一次迁移如何设置门禁

发表于2026-11-07|更新于2026-11-07|AI 3D 游戏生成
|总字数:1.8k|阅读时长:5分钟|浏览量:|评论数:

游戏生成平台保存的不只有用户和项目，还包括 Agent 运行记录、步骤、生成资产版本与沙盒版本。数据库从 MySQL 切到 PostgreSQL 时，直接逐表导入并不足够：旧任务是否仍在运行、目标库是否干净、JSON 与枚举能否映射、文件路径是否仍然有效，都可能决定切换能否完成。

本文复盘项目在 2026 年 8 月从 MySQL/Prisma 迁移到 PostgreSQL/Prisma 的历史过程。它聚焦一次性的维护窗口迁移工具，不代表当前日常部署方式。当前 README 仍将 tools/migration 定义为 MySQL → PostgreSQL 的维护窗口工具；业务数据库日常变更走 Prisma migrations。

背景与目标

早期单体阶段，项目用 MySQL 存储账号、游戏项目、资产和 Agent 任务。随着系统拆成 Web、NestJS API 与后台 Worker，数据库开始承担更多任务协作和结构化数据职责。2026 年 8 月的架构重构把 ORM 统一到 Prisma，并将主数据库切为 PostgreSQL。

迁移目标是保留旧业务记录及其关联，让新的 PostgreSQL 数据库可以继续承载项目、资产和历史运行数据。旧会话不会迁移，用户需要重新登录。当前数据库 schema 已经继续演进，因此这套脚本应被理解为对应早期 schema 的一次性工具，不能直接用于任意 MySQL 库或今天的生产数据。

端到端流程

项目把切换安排在维护窗口。先停止旧 Web 与 Worker 的写入，备份数据库和本地沙盒、上传目录，再检查旧库没有 running 状态的 AgentRun，并确认 PostgreSQL 目标库为空。工具依赖这些前提，没有提供在线双写或增量追平机制。

    flowchart LR
  A[进入维护窗口] --> B[停止旧 Web 与 Worker 写入]
  B --> C[备份数据库与沙盒、上传文件]
  C --> D{旧库还有运行中的 AgentRun？}
  D -->|有| X[中止迁移并处理任务]
  D -->|没有| E{PostgreSQL 目标库为空？}
  E -->|否| Y[中止并准备干净目标库]
  E -->|是| F[事务内按依赖顺序复制核心表]
  F --> G[规范化 JSON、枚举与存储路径]
  G --> H[回填资产当前版本并重置序列]
  H --> I[检查关键外键关系并复制文件]
  I --> J[提交事务并检查迁移报告]
  J --> K[部署新版本并核对业务数据与文件]

迁移工具的关键处理

脚本位于 tools/migration/src/mysql-to-postgres.ts。它按主键顺序处理用户、项目、资产、资产版本、生成任务、Agent 运行、步骤、项目资产规格、沙盒版本和消息等 10 张核心表。每行写入 PostgreSQL 参数化查询；所有数据库插入和更新放进一个事务，异常时回滚数据库事务。

转换逻辑针对当时的 schema 做了明确约束：

  • JSON 字段先规范化为可写入值，避免把非 JSON 字符串误当结构化内容。
  • 枚举值经过白名单校验，遇到未支持状态就停止，避免悄悄写入错误状态。
  • 本地存储对象键与沙盒路径被改写成相对路径，减少旧机器路径残留。
  • agent_steps 中冲突的阶段尝试次数会递增，满足新库唯一约束。
  • assets.current_version_id 在资产版本插入后再回填，处理双向关联的顺序依赖。
  • 自增序列在导入后重置，并执行一项 AgentRun 到 Project 的孤儿关系检查。

迁移结果会按表输出行数和 SHA-256 摘要，便于留存运行记录。摘要针对规范化后的迁移行生成，可用于比对运行产物；它本身不等价于源库与目标库的完整逐字段校验。

数据事务与文件迁移的边界

沙盒与上传文件不在 PostgreSQL 事务中。脚本在数据库事务期间递归复制目录，文件复制不能随 SQL ROLLBACK 自动撤销。若复制中途失败，目标目录可能留下部分文件；重新执行前应检查目标目录并按维护计划清理或换用空目录。

这也是“数据库事务成功”不能代表“整个应用切换完成”的原因。完成迁移后还要核对文件数量、对象键能否读取、资产缩略图与沙盒预览路径是否有效，并抽查用户、项目、资产版本和运行记录的关联。失败时应保留旧系统和备份，按维护窗口的回退方案恢复服务。

操作入口与配置边界

项目根目录保留了一次性命令：

连接串和文件目录应通过本机环境配置提供，不写入博客、提交记录或终端截图。日常 schema 更新使用 Prisma 的开发或部署迁移命令；migrate:mysql 仅对应从旧 MySQL 方案切换到 PostgreSQL 的维护工作。

上线前还要为数据迁移制定人工操作清单，包括维护窗口、旧服务停写确认、备份位置、目标库确认、迁移报告保存、抽样核验和回退负责人。代码中的预检查只能覆盖脚本明确检查的条件，不能替代运维核验。

可复用的经验与踩坑提醒

  1. 迁移前先冻结写入。 这份工具没有双写和增量同步，迁移期间继续接收任务会造成数据边界不清。
  2. 把旧任务状态当成前置条件。 脚本遇到运行中的 AgentRun 会停止，应该先判断任务如何完成或取消，再安排维护窗口。
  3. 目标库必须干净。 导入脚本按记录插入，不是 upsert。已有数据会产生冲突，也可能造成重复或部分写入。
  4. 显式列出特殊映射。 JSON、枚举、自增序列、文件路径和循环关联都需要逐项处理，不能只靠数据库类型转换。
  5. 数据库与文件分开验收。 SQL 可以回滚，复制的文件不会自动回滚；分别记录和核对两类结果。
  6. 一次性脚本要绑定 schema 版本。 源表名、字段和状态集合变化后，应重新审查映射，不要把历史工具当成通用导入器。

结论

这次迁移的核心做法，是把业务切换变成有明确门槛的维护流程：停写、备份、检查任务与目标库、事务导入、处理特殊关系、复核文件和业务数据，再切换新版本。显式失败条件让不兼容数据尽早暴露；而数据库事务与文件系统边界的区别提醒我们，恢复与验收必须覆盖整个应用的数据面。
