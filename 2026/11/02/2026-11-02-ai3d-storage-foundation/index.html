从项目早期讲起：模型文件的存储键、磁盘路径与访问地址

发表于2026-11-02|更新于2026-11-07|AI 3D 游戏生成
|总字数:2k|阅读时长:6分钟|浏览量:|评论数:

3D 游戏平台会保存模型、贴图、缩略图与截图。文件能在开发机上打开，只是第一步；数据库还要能定位它，后端要能读取它，浏览器要拿到适合访问的地址。

本文继续整理早期基础，聚焦存储表示与适配层，不重复此前资产输入、生成和场景导出的工作流。对照 2026 年 8 月 3 日提交 fabfabfb，当前 lib/uploads.ts 与 NestJS 存储包装服务保持一致；底层适配器后来补充了读取等能力。下文按当前代码说明行为，不把新增能力都归为早期实现。

先分清四种位置

表示 示例或用途
bucket 区分资产所在存储桶，本地实现返回 local
objectKey 对象在存储系统内的键，例如 assets/users/<user>/models/<asset>/v1/tree.glb
磁盘路径 本地存储根目录与对象键解析后的实际文件位置
URL 浏览器获取文件的地址，由具体适配器生成

示例中的用户与资产编号都是占位符。objectKey 不是磁盘绝对路径，也不等于完整 URL。URL 可能随着域名、代理或存储供应商配置变化；业务数据保存 bucket 和 objectKey，读取时再选择适配器，有助于将文件定位与访问方式分开。

上传到可读取资产的主要流程

    flowchart TD
  A[上传模型与可选缩略图] --> B[检查大小与扩展名]
  B --> C[创建 uploading 资产记录]
  C --> D[选择本地或云端存储]
  D --> E[写入对象并获得 bucket 与 key]
  E --> F[保存资产版本与当前引用]
  F --> G[标记 ready]
  G --> H[请求文件访问地址]
  H --> I[检查资产归属并选择存储适配器]
  I --> J[生成 URL 或重定向]

图中是当前私人资产接口的正常路径。公开资源库另有访问规则，不能把这里的归属检查推断成所有资源请求都采用同一授权方式。

存储接口让业务代码关注对象

apps/backend/src/lib/storage/StorageService.ts 定义当前接口：

配置选择器支持 Local、MinIO 和七牛适配器。NestJS 的 StorageService 则提供 current、forTarget、forBucket 等包装入口，让业务服务按目标或已有记录选存储。

forTarget("local") 明确选择本地；选择 cloud 时，如果全局驱动仍是 local，会报未配置远程存储。它没有把用户明确选择的云端写入静默降级为本地保存。

读取已有资产时，forBucket() 会识别 local，以及与配置匹配的远程 bucket；无法匹配时回退到当前默认适配器。这意味着更改驱动并不自动迁移旧文件，也不能保证任意历史 bucket 都能被新配置正确识别。

本地实现怎样生成路径与 URL

LocalStorageService 规范化对象键中的分隔符，解析本地目标路径，创建父目录并写入 Buffer。返回 bucket 为 local，objectKey 为规范化后的键。

生成访问地址时，它使用 LOCAL_STORAGE_PUBLIC_BASE_URL 拼接对象键；这一步本身不读取文件，也不检查外部代理是否已经正确暴露该路径。所以“生成了 URL”与“浏览器能成功下载文件”需要分别验证。

本地适配器虽然有路径前缀检查，但不能据此称为完整文件隔离：当前检查方式仍需关注目录边界和符号链接等问题。路径规范化、访问权限和实际文件服务应当一起评估，本文不将某个字符串检查包装成完整安全保证。

资产状态和版本记录各管什么

当前 AssetsService.upload() 先检查文件大小与扩展名，再创建 uploading 记录。主文件限制为 50MB，缩略图在服务层另有 8MB 限制。扩展名白名单包含 glb、gltf、bin、ktx2、hdr、exr 及常见图片格式；这项检查不等于深度解析文件内容或验证模型可渲染。

对象键按用户、资产和版本组织，文件名中的特殊字符会被替换。文件写入后，服务创建 AssetVersion，并把当前资产引用指向这个版本，最后标记 ready。

这能区分“有一条记录”和“文件已可用”。但对象存储写入与数据库操作不是同一个事务：如果主文件已经上传，而缩略图或版本记录保存失败，catch 会将资产标记 failed，并未在这里完整补偿所有已写入对象。运维清理不能只看成功记录，还应考虑这些中间状态。

私人文件接口先检查归属

AssetsService.url() 先调用 owned，确认资产属于当前用户，再选择主文件或缩略图键。键缺失或仍为 pending 时返回文件尚不可用。

控制器有两种形式：/assets/<id>/url 返回 { url }，而 /assets/<id>/file 和 thumbnail 接口返回重定向。它们都复用获取地址的服务逻辑。

授权检查发生在获取地址这一层。最终 URL 是否公开、是否有有效期，仍取决于适配器和文件服务配置。数据库中的 private 标记不能单独证明一个已经获取的直链不可被其他人使用，也不能把方法名 getPublicUrl 理解成所有驱动都采用相同访问策略。

uploads 路径工具是另一套约定

截图等上传文件还会使用 lib/uploads.ts：它从 UPLOAD_ROOT 或默认目录定位上传根，数据库可保存相对路径，读取时由 resolveStoredUploadPath() 解析。

上面仅摘出相对路径表示的步骤，实际函数先执行解析与根目录检查。它与资产 bucket/objectKey 机制用途不同，不能把一个对象存储键直接交给截图路径工具，或把磁盘路径当成浏览器 URL。

排查丢图时，应先问记录使用哪一种表示，再查根目录、bucket 配置和访问地址。也要确认 API 与执行文件任务的进程能访问同一份存储，不能只验证某一台机器上文件存在。

删除、验证范围与工程经验

当前资产删除会收集当前对象和各版本对象，按 bucket 与 key 去重，先删除文件，再删除数据库记录。这样避免对同一引用重复删除，但对象删除与数据库删除仍不是原子操作；部分文件删除失败或后续数据库失败时，需要结合记录和存储实际状态排查。

今天核对了历史 diff、存储接口、驱动选择、本地实现、资产上传和读取调用链，以及 uploads 路径工具。没有读取实际存储凭据、上传真实用户文件或调用云服务；这些说明来自代码检查，不代表跨驱动上传、下载和删除已经完成端到端验收。

可复用的经验是让每一种位置有明确职责：bucket 与 key 定位对象，根目录与相对路径定位本地文件，URL 提供访问入口，状态字段描述处理进展。发生失败时，再分别核对文件、元数据和外部访问是否一致。

这套存储基础让模型、图片和截图可以被持续定位与复用。将它与版本、权限和请求链路放在一起理解，才能看清游戏生成平台怎样把一次产物保存变成长期可维护的数据能力。
