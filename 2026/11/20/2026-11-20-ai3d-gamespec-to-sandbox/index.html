从 GameSpec 到源码沙盒：AI 3D 游戏生成架构的两次转向

发表于2026-11-20|更新于2026-11-27|AI 3D 游戏生成
|总字数:1.6k|阅读时长:5分钟|浏览量:|评论数:

AI 生成 3D 游戏，最初可以被看作“让模型填写一份游戏规格，再由固定 Runtime 负责运行”。这套受控方案容易校验，也能复用统一的 Three.js 能力；当项目希望支持超出模板的玩法时，规格语言本身却成了上限。本文根据项目早期需求文档与当前架构记录，回顾这次从 GameSpec 到自由源码沙盒的演进。这里会明确区分历史方案和当前实现，避免把旧 Runtime 当作现行机制。

背景与目标

早期需求文档描述的是 Next.js 单体应用：用户输入自然语言，系统生成受控 JSON（GameSpec），规划并生成缺失的 3D 资产，最后由主应用里的 three.js Runtime 解释规格、组装可交互小游戏。LLM 不直接输出可执行代码，MySQL 保存项目、规格、资产元数据和任务状态。

这个边界有实际好处：结构可用 Zod 校验，Runtime 的行为可预测，生成结果也能复用资产与组件。但早期文档同时记录了关键限制：GameSpec 仍以模板生成为主，真实模型输出尚未完全产品化；Runtime 规则和 AI 生成的模型加载也需要继续解耦。玩法一旦超出已定义的字段和模板，模型即使“想得出来”，系统也没有办法表达。

第一代：让模型填规格，让 Runtime 执行

第一代端到端链路可以概括为：

    flowchart LR
  A[自然语言提示词] --> B[生成受控 GameSpec JSON]
  B --> C[Zod 结构校验]
  C --> D[资产需求规划]
  D --> E[查询或生成 3D 资产]
  E --> F[Three.js Runtime 解释规格]
  F --> G[浏览器交互预览]
  C -->|无效或不支持| H[修复、降级或提示用户]

核心设计是把“游戏设计”压进一个稳定的数据契约。下面只是说明这种模式的示意结构，并非仓库中某个现行 API：

Runtime 需要理解每个字段的含义，并将其映射到场景、实体、碰撞和胜负规则。新增一种玩法，通常意味着同时扩展 schema、模型提示词、资产规划和 Runtime；如果模型输出了 schema 尚未支持的能力，只能要求它重试、降级，或把需求拒之门外。

为什么转向完整工程源码

项目后来引入 NestJS、PostgreSQL 和 Worker，随后进一步采用 Deep Agents 与 Docker 沙盒。当前架构记录明确写明：主应用不再维护 GameSpec DSL 与游戏 Runtime；Agent 为具体游戏生成完整前端工程，沙盒负责构建与验收。相机、状态、碰撞、物理和组件选择由生成工程决定。

这不是“取消约束”，而是把约束从游戏表达层移到执行边界：模型可以为不同玩法选择不同代码结构，系统则通过隔离目录、拒绝符号链接、不给宿主密钥、限制依赖来源、禁用安装脚本，以及容器资源和网络限制来控制执行风险。构建结果仍要经过服务端验证，不能仅凭 Agent 的文字回复宣称成功。

    flowchart TB
  subgraph old[历史方案：受控 DSL]
    P[用户提示词] --> S[GameSpec JSON]
    S --> R[主应用 Three.js Runtime]
    R --> G[固定模板游戏]
  end
  subgraph now[当前方案：源码 + 隔离执行]
    U[用户目标] --> A[Agent 编写完整前端工程]
    A --> V[路径与依赖校验]
    V --> D[Docker 隔离环境构建]
    D --> Q{构建和预览验收通过？}
    Q -->|是| O[形成可发布版本]
    Q -->|否| F[返回错误并继续修复]
  end

关键难点与工程取舍

表达能力与可预测性的交换

固定 DSL 让解释器容易理解，却要求每种玩法都能预先编码。自由源码扩大了表达范围，也增加了依赖安装、构建失败和资源滥用的风险。工程上要把“生成什么”与“在哪里执行”拆开：前者可灵活，后者必须受限并可验证。

验收不能等同于模型自述

Agent 可能报告“游戏已经完成”，但文件不存在、依赖不兼容或构建失败。可靠的完成条件应来自工具结果：输入目录通过校验、依赖满足策略、构建命令退出成功，且产物满足发布要求。失败时保留明确错误供 Agent 修复，而非把自然语言描述当作事实。

旧文档和旧目录会误导读代码

仓库仍可能留有早期需求文档、空目录或旧入口。阅读时应同时核对文档更新时间、Git 历史、当前脚本和实际调用路径。项目架构解析文档将旧 GameSpec 需求文档标记为过期；因此文中第一代链路是历史复盘，不是今天运行中的实现。

可复用经验与踩坑提醒

  • DSL 适用于玩法边界明确、模板长期稳定的产品；当每个用户需求都可能改变交互模型时，扩 DSL 的成本会持续累积。
  • 从 DSL 迁移到源码，不代表放弃类型、权限或质量门禁。应把验证从“规格是否符合 schema”扩展到“文件、依赖、构建与运行产物是否满足约束”。
  • 安全规则必须落在服务端和执行环境中，不能依赖提示词要求 Agent 自律。
  • 演进记录要同时保留“当时为什么这样做”和“现在为什么替换”，否则历史文档很容易被误读成当前操作手册。

结论

GameSpec 方案以受控 JSON 换取可预测性，适合早期快速跑通固定类型的 3D 游戏闭环；当玩法表达被模板限制后，项目转向让 Agent 生成完整前端工程，并由 Docker 沙盒负责隔离和验收。这个演进的核心不是追求更自由的模型，而是重新划分职责：游戏表达允许变化，执行安全与发布质量由工程边界兜底。
