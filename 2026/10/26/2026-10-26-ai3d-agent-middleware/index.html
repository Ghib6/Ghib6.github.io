Agent 中间件可插拔，有边界：统一组装、依赖校验与执行保护

发表于2026-10-26|更新于2026-10-26|AI 3D 游戏生成
|总字数:2.3k|阅读时长:7分钟|浏览量:|评论数:

3D 游戏生成平台有多种 Agent 入口：Supervisor、设计与开发子角色、直接修改 worker，以及只读问答。它们都要处理上下文、文件工具和业务状态，但不能拥有完全相同的权限与执行行为。

如果每个入口各自维护一份中间件数组，一处新增停止检查，另一处可能漏掉；关闭聊天状态提示，也可能意外关闭原本藏在同一模块里的执行保护。10 月 25 日的重构将这些规则集中到 createGameMiddleware()，同时明确哪些增强功能可以关闭，哪些约束必须保留。

本文依据当前本地源码与配套文档复盘。今天实际重跑了组装回归测试，没有追加付费模型调用，也没有修改生成游戏。

一个组装入口，多种角色配置

统一入口位于 apps/agent/src/agent/middleware/index.ts。调用方传入 profile、角色、工作目录、结果存储及所需能力，工厂组装应用中间件，再交给 LangChain 的 middleware 配置。钩子的实际执行仍由框架负责。

当前 profile 包括 supervisor、planner、developer、edit 和 question。例如 Supervisor 可以有待办计划，开发与直接修改角色可使用修改目标，问答角色则不提供写入或交接工具。

    flowchart TD
  A[生成、子角色、编辑、问答入口] --> B[角色与能力配置]
  B --> C[createGameMiddleware 统一组装]
  C --> D[检查重复注册与模块依赖]
  D -->|不合法| E[创建 Agent 时直接报错]
  D -->|合法| F[状态契约与中间件交给框架]
  F --> G[模型调用前执行检查与上下文处理]
  G --> H[模型选择工具]
  H --> I[工具执行前再次检查任务状态]
  I --> J[按角色权限执行与记录业务结果]
  J --> K[检查点保存与后续执行]

这是一张职责示意图，不是每个钩子严格按箭头依次运行的调用栈。beforeModel、afterModel 与包装钩子的执行语义由 SDK 决定；应用工厂固定注册顺序，并用回归测试验证关键组合行为。

为什么“状态提示”与“执行保护”要分开

聊天栏的“正在读取源码”属于展示增强。停止请求是否生效、任务是否仍有效、费用状态是否健康，则是执行规则。两者不应共享一个开关。

重构后，独立的 GameExecutionGuard 在模型调用前与工具调用前运行检查，还负责可选的在途工具跟踪。活动提示模块只处理其自己的事件展示职责，统一组装时避免重复跟踪。

第二次检查尤为重要：模型开始调用时任务有效，不代表模型返回工具请求时任务仍有效。用户可能在等待模型输出期间点击停止。若工具前不再检查，一次已排队的 edit_file 仍可能写入候选源码。

这些能力也依赖调用方正确传入任务检查与预算对象。工厂提供统一接入位置，并不凭空获得数据库租约或预算配置；验证时仍应看生产入口如何接线。

可选模块和必需约束的边界

features 当前只控制三个增强模块：活动提示、无进展纠正、具体修改目标。它是代码配置，没有新增面向用户的界面开关。

关闭这些模块，仍然保留执行保护、角色工具权限、源码版本验证、真实修改交接，以及已配置预算时的费用保护。关闭活动提示也不等于删除所有业务事件：结构化交接记录仍要保留。

模块或规则 本次配置中的定位
activity 可选聊天状态提示
progress 可选无进展纠正
editFocus 可选具体修改目标记录
executionGuard 独立执行保护
taskContract 写入角色的真实交接等业务约束
readLedger 源码交付范围与版本验证
filesystem 按角色提供的文件工具与权限
budget 传入预算对象后启用的费用保护

问答配置不允许 filesystem: "write"。这让错误配置在创建 Agent 时就被拒绝，而不是期待模型“自觉不写文件”。

依赖校验：在任务开始之前发现组装错误

中间件有真实依赖。上下文处理需要工具策略；无进展纠正需要任务契约和读取账本；修改目标需要读取账本。把模块拆成多个文件，并不意味着业务关系已经消失。

工厂检查重复标识、重复中间件名称，以及缺失依赖。例如仅注册 editFocus 却遗漏 readLedger，应立即报错。这样错误发生在创建 Agent 阶段，而不是执行到一半才发现状态字段或工具策略缺失。

当前工厂还固定了兼容的注册顺序。依赖检查主要确认模块存在，不能把它说成能够自动推导任意排序，或证明任意第三方中间件组合都安全。

状态契约独立，恢复不依赖导入实现模块

原先多个服务兼顾状态字段和执行逻辑，其他模块为复用状态定义，可能被迫导入整份中间件实现。现在 state/*.ts 只定义任务、读取、修改目标、工具集合和语义进展的 checkpoint 契约，再由 state/index.ts 汇总。

工厂首先注册只声明状态、没有执行钩子的 GameCheckpointState。文件快照与真实差异计算独立到 workspace-evidence.ts，共享交接异常也独立到 task-errors.ts。

本次文档说明状态字段名、结构和归约行为保持兼容，没有要求数据库迁移。重点不是目录看起来更整齐，而是状态类型、合并规则与执行钩子可以分别检查；关闭增强模块后，必要的恢复证据仍然存在。

摘要逻辑统一，策略差异显式保留

生成入口和直接编辑入口共用一个上下文适配实现，摘要算法仍来自官方 createSummarizationMiddleware。应用负责组合角色工具策略、业务状态和容量处理。

生成路径保留 24,000 Token 触发、8,000 Token 近期保留目标；直接编辑路径保留 16,000/6,000，集中为具名策略。这些是仓库当前配置，不是对所有模型和任务的通用推荐。

只有存在明确 HTTP 容量保护时，才使用容量适配模型压缩旧工具正文；默认直接使用官方中间件。任务要求、上一份摘要与结构化账本不能被简单尾部截断。应用适配代码集中在 context.ts，便于 SDK 升级时核查公开钩子与状态接口。

测试在关闭三个可选模块后，仍通过真实 SDK 文件工具完成读取、修改与核对交接，共三次模拟模型请求；同时确认账本与任务基线保存。它还验证缺失或重复依赖拒绝、只读问答权限，以及关闭提示后停止检查仍生效。

针对更容易遗漏的停止时机，测试在模型返回后、工具执行前触发停止，确认真实文件没有被后续工具修改。测试使用临时目录和模拟模型/HTTP，没有供应商请求。

配套文档另记录了此前的全量测试、类型检查、定向 lint、生产编译和容器验收；全量 lint 仍有既有 CJS 规则错误。本文不把那些已有记录冒充今天重跑的结果，也不据此断言任意长任务都已通过真实生成验收。

结论

这次重构把多入口共享规则集中到一个工厂，同时将可选增强、持久状态和执行约束拆清。对复杂 Agent，统一组装能减少遗漏；独立执行保护则保证展示功能的调整不会顺带改变停止和权限语义。

后续增加模块时，值得继续保持这一习惯：声明真实依赖，在任务启动前检查组合，用实际写入和停止时机验证边界，而不仅检查数组里是否出现了某个中间件名称。
