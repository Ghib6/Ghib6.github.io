AI 反复读源码却不动手？3D 游戏 Agent 的读取账本与精确恢复

发表于2026-10-23|更新于2026-10-23|AI 3D 游戏生成
|总字数:2k|阅读时长:6分钟|浏览量:|评论数:

用户要求“优化操作手感和相机”，Agent 却不断检查文件、翻页、再检查同一段源码。调用次数在增加，真正的修改迟迟没有出现。这是 3D Game Agent 在近期调试中遇到的实际问题。

10 月 22 日的改造围绕三个事实展开：哪些源码确实交付给过模型、这些源码现在是否仍然有效、模型下一步准备修改什么。本文基于本地实现与验收记录整理；涉及真实模型的历史结果均来自项目已有诊断文档，今天没有追加付费测试。

问题出在哪里：有读取记录，不等于有可用证据

一次源码观察同时涉及三种信息：服务端检查过的文件清单、响应实际交付的行范围、模型当前上下文里仍保留的正文。三者不能互相替代。

项目诊断记录指出，早期实现曾在工作上下文达到固定字符阈值时，仅保留最新完整源码结果。模型拿到后一页时，前一页可能已经被压缩；为了精确修改，它又请求前一页，造成相邻页之间来回补读。该阶段甚至没有触发摘要模型，说明不能把所有重复读取都归因于摘要质量。

修复移除了生产默认的这一提前字符截断，让上下文主要按官方摘要机制与溢出恢复处理。只有显式配置 HTTP 容量保护且接近容量时，才预先压缩旧源码。

第一步：把源码交付做成可核对的协议

inspect_project 的小结果直接返回，大结果按文件和完整行分页。源码响应预算为包含 JSON 包装的 24KiB，而非正文单独占满 24KiB。

响应中的 source 记录本页实际交付范围，files 是服务端读取清单，remainingSources 描述结果游标之后尚未返回的范围。结果页游标与文件源码行偏移属于不同坐标，调用方必须分别使用。

    flowchart TD
  A[定位相关源码] --> B[按完整行返回正文与版本]
  B --> C[账本记录实际交付范围]
  C --> D{当前版本与证据一致吗}
  D -->|否| E[补读当前版本]
  E --> C
  D -->|是| F{精确正文仍在上下文吗}
  F -->|否| G[按引用或范围恢复正文]
  G --> H[声明局部修改意图]
  F -->|是| H
  H --> I[修改、核对差异与交接]
  I --> J[构建与交互验收]

源码引用由任务范围和内容确定，重复请求可以复用未过期引用。读取引用时重新校验 SHA-256 版本；源码改变返回 STALE_SOURCE，引用失效返回 REFERENCE_EXPIRED，避免拿着旧证据修改新文件。

第二步：账本独立于摘要，记录范围而非复制源码

LangGraph 的 gameReadLedger 持久保存角色、工具调用标识、文件版本、已交付行范围、结果页索引和引用，不把整份源码再存一遍。每次模型请求前，程序重新核对版本，并注入合并后的交付进展。

并行结束和重读旧页时，不能把“最后返回的页码”直接当成最新进度。实现对已交付行范围与结果行索引取并集，从连续已交付索引计算下一处缺口。因此后返回的旧页不会让游标倒退；到达结果尾，也不意味着此前每页均已交付。

旧 checkpoint 只有明确的交付范围才会被恢复为已读证据，没有范围的记录保持未知。这个保守选择避免模型把一份目录清单误当成“所有文件都读完了”。

账本也不保证正文仍然可见。它提供的是找回精确证据的索引；需要逐行编辑时仍应恢复对应正文，不能仅凭“此前读过”的标签猜测实现。

第三步：让读取服务于具体修改

新增 record_edit_focus 保存局部修改意图、证据版本与范围，不保存源码正文。摘要后必要时从已交付消息恢复有限正文；缺证据可以继续读，证据范围或版本更新后重新评估修改意图。

这里没有通过禁止读取来强迫模型写代码。更有效的约束是让模型回答：准备修改哪个局部行为，依据哪份当前证据，还缺什么信息。

相机与操作手感这类可独立验证的目标，也改为默认串行委派，由父 Agent 聚合完成度。每个开发子任务有自己的交付基线，避免前一个子任务留下的账本阻挡后续合理读取。

摘要模板则固定保留用户要求、约束、已确认事实、拟修改点、实际改动、验证、未决问题和下一步，并合并上一份摘要。项目配置的摘要目标为 24,000 Token、近期上下文保留目标为 8,000 Token；这些是上下文管理参数，不应解释成生产任务调用次数上限。

验收怎么读：成功路径和试错成本都要保留

项目诊断记录显示，最终一次真实验收完成了 3 个文件的修改、结构化交接、构建、交互和私有版本保存。最终轮共 29 次模型请求、357,911 Token，首次写入发生在第 7 次工作调用。

但这不是全部试错成本：记录中的九轮真实测试合计 2,981,490 Token，前面多轮因预算预留不足停止。不能只拿最终一轮与旧失败任务比较，声称获得相同完成度下的成本降幅。

还有两个重要边界：最终真实成功轮没有触发摘要；连续三次摘要后仍能写入与交接，来自离线回归。视觉模型当时未配置，最终私有版本为 needs_review，不能称作视觉评审通过。一轮成功也不能证明任意任务都不会再次循环。

今天实际重跑了项目现有定向测试：

测试通过，覆盖源码内联与分页、24KiB 包装预算、引用、版本变化、恢复、相邻页同时可见、旧记录，以及连续三次摘要后的实际写入和已核对交接。这些测试支持的是对应协议与回归场景，不是今天重新完成了一次真实游戏生成。

可复用的工程经验

  1. 交付元数据由程序生成。 文件清单、已交付范围和当前版本分别记录，避免让自然语言摘要承担事实数据库的职责。
  2. 上下文压缩先检查证据损失。 省掉刚收到的相邻源码页，可能换来更多重复调用；诊断要查看真实模型输入，而不只看工具调用计数。
  3. 精确修改需要正文。 账本和摘要负责定位，引用恢复负责补齐细节，两者一起才能支持编辑。
  4. 完成要靠差异与验收。 读取进度、修改意图都只是中间状态，真实文件改动、结构化交接和构建交互结果才是后续依据。

这次修复的价值，是把“Agent 似乎记得读过什么”变成能核对版本、范围和修改结果的执行流程。对于复杂 3D 游戏代码，稳定地从观察走向修改，比单纯增加可读文件数更能推动任务完成。
