源码 ZIP 导入：让 AI 3D 游戏从依赖安装走到可玩预览

发表于2026-10-24|更新于2026-10-24|AI 3D 游戏生成
|总字数:2k|阅读时长:6分钟|浏览量:|评论数:

AI 3D 游戏生成平台除了从零生成，还需要接住用户已有的作品。上传一份源码 ZIP 后，平台必须找到项目入口、识别包管理器、安装依赖、执行构建，再把静态产物变成可预览的游戏。

10 月 23 日，项目为单项目 npm/pnpm 源码包补充了明确的依赖安装计划。本文依据当前本地源码和配套文档复盘；今天实际运行的是导入回归测试，没有运行真实 ZIP 的 Docker 集成验收。

一条导入链路，多个失败边界

源码包需要 package.json 中提供非空的 scripts.build。导入器在验证依赖和包管理器之后，将源码复制进任务独占 Docker 卷，安装阶段允许联网，构建阶段禁用网络。构建成功后，再检查输出目录中的静态游戏文件。

    flowchart TD
  A[上传源码 ZIP] --> B[校验归档路径并定位项目根目录]
  B --> C[验证 build、依赖声明与锁文件]
  C --> D[确定包管理器与明确版本]
  D --> E[独占卷内安装依赖]
  E --> F{安装成功吗}
  F -->|否| G[清理前收集有限失败日志]
  F -->|是| H[禁网执行 build]
  H --> I[检查静态输出目录]
  I --> J[新卷内加载产物并截图]
  J --> K[供后续预览与导入流程使用]

这里最值得注意的是：安装、构建、预览是不同阶段。安装成功不能证明构建成功，截图成功也不能证明所有玩法和外部资源都正常。

难点一：不能默认所有源码包都用 npm

导入器首先读取 packageManager。存在声明时，必须是 npm 或 pnpm 的明确版本；实现也接受指定格式的 Corepack SHA 后缀。否则根据锁文件判断：有 pnpm 锁文件则使用 pnpm 10.18.3，其他情况使用 npm 11.6.2。这里的版本号是仓库当前的回退配置，并不表示最新版本。

输入情况 当前选择或处理
packageManager: pnpm@10.18.3 使用声明版本，并核对锁文件类型
只有 pnpm-lock.yaml 使用 pnpm 回退版本
有 package-lock.json 使用 npm，并运行 ci
没有锁文件 允许安装，日志标明未提供锁文件
同时存在 npm、pnpm 锁文件 明确拒绝，要求选择实际使用的一份
声明 npm 却携带 pnpm 锁文件 明确报告不一致

Yarn、monorepo、pnpm workspace 以及非空的自定义 pnpm 配置，目前不在支持范围。提前返回说明能让用户知道该重新打包什么，而不是等到容器里产生难以理解的错误。

需要区分一个细节：代码接受声明中的 SHA 后缀，但随后提取版本并从 npm registry 安装工具。不能仅凭“接受该格式”就声称已经按该后缀验证了包管理器完整性。

难点二：锁文件应成为约束，而不是失败后被删除

有 npm 锁文件时使用 npm ci；有 pnpm 锁文件时使用 pnpm install --frozen-lockfile。清单与锁文件不同步时，让安装明确失败，能保留用户原先的依赖约束。

如果平台为了“自动修好”而删除锁文件，某次导入可能拉到不同的依赖版本。对于 Three.js、R3F、物理库和构建插件之间存在兼容关系的游戏工程，这会把一个依赖问题变成难以复现的运行时问题。

这是项目声明片段，实际提交仍需要完整源码、依赖声明及与之匹配的锁文件。未带锁文件虽然可以安装，但应理解为依赖解析可随时间变化的路径。

难点三：安装能联网，构建仍要隔离

上传的源码是待执行输入。当前实现把包管理器安装到独占卷内的 .import-tools，与游戏依赖树分开放置，构建容器复用这份工具。

依赖安装禁用生命周期脚本，pnpm 还禁用 pnpmfile hooks。项目依赖声明和锁文件会检查 Git、外部 URL、本地路径或链接依赖；当前只接受相应的 npm registry 依赖范围。

构建阶段仍显式执行用户的 scripts.build，因此禁用安装脚本并不等于没有运行用户代码。执行容器使用只读根文件系统、非 root 用户、资源限制和禁网设置，工作卷保持可写以容纳依赖及产物。只读根文件系统不能理解成整个工程只读。

源码准备阶段只复制本次任务文件，不挂载共享沙盒卷、宿主 Docker socket 或应用凭据。构建之后的截图阶段则建立仅含已检查产物的新卷，避免预览过程继续携带整份源码和安装工具。

这些机制各有边界。例如安装阶段使用 bridge 网络并指定 registry，不等于容器网络已经实施完整的域名白名单；不能把依赖来源检查描述成所有出站连接都被拦截。

难点四：容器清理之后，错误证据也可能没了

npm 缓存位于临时文件系统。安装失败后若立即删除容器，debug 日志也会消失，最终用户只得到“导入失败”。

当前 runner 在安装命令退出失败时，先输出 npm debug 日志尾部，再返回原退出码。Docker 包装层限制返回内容大小，任务流程保留有限错误信息，避免复制整个缓存。

这条经验适用于多数短生命周期构建环境：失败证据必须在销毁前收集。日志也只是诊断材料，公开分享前仍需检查是否含路径、凭据或其他私人内容。

静态产物是下一道契约

构建完成后，导入器检查指定输出目录；未指定时依次尝试 dist、build、out，再调用产物树检查。当前支持的是静态浏览器游戏，需要找到相应入口，而不是启动长期运行的 Node 服务。

游戏还应尽量把模型、贴图、音频等资源打包到本地产物中。即使源码构建通过，运行时继续请求外部模型或 CDN，仍可能在隔离预览中失败。构建可复现与运行可离线是两个需要分别验收的目标。

今天验证了什么

今天实际执行了仓库的导入回归命令，结果通过：

测试覆盖 ZIP 解压、路径与大小限制、符号链接拒绝、npm/pnpm 安装计划、锁文件冲突、外部依赖拒绝、资源 URL 重定位和预览授权。它验证了对应代码规则，没有执行真实依赖下载、Docker 构建与浏览器截图。

仓库另有 game-import.integration.ts，需要明确提供源码 ZIP 和 Docker 环境，才会执行真实安装、构建与截图。今天没有追加运行，因此本文不把集成入口的存在当作真实通过的证据。

结论

这次改造把源码导入中的隐含假设变成了明确规则：使用哪个包管理器、锁文件是否一致、哪个阶段允许联网、输出是什么，以及失败后保留哪些证据。

对 AI 3D 游戏平台而言，接入已有源码同样是一条交付流程。让输入可判断、构建可定位、产物可检查，用户才能从“传上来一个 ZIP”走向稳定的试玩与后续创作。
