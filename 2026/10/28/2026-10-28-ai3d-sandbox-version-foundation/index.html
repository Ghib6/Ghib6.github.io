从项目早期讲起：AI 3D 游戏的源码、预览与版本恢复如何保存

发表于2026-10-28|更新于2026-10-28|AI 3D 游戏生成
|总字数:2.5k|阅读时长:8分钟|浏览量:|评论数:

AI 生成了一份能运行的游戏代码，距离“用户可以放心继续修改”还有几步：新的修改不能破坏当前能玩的游戏，历史版本必须找得回来，下载的源码和浏览器中的预览也要各有明确来源。

这篇从项目早期的基础模块讲起。对照 2026 年 8 月 3 日提交 fabfabfb 与当前工作区，后端 sandboxWorkspace.ts、sandboxPaths.ts 和 sandboxService.ts 三个文件没有差异。候选目录、活动指针、源码快照与归档因此适合作为长期知识沉淀。本文同时核对当前 Agent 的产物保存与后端恢复入口，明确后续补充的行为，避免用旧代码解释今天的整个系统。

先确定需要保住什么

最容易理解的需求是：用户已经有一个可玩的 v1，接着让 AI 修改角色移动速度。生成或构建 v2 可能失败，但 v1 应继续可访问；v2 成功后，用户也应该还能恢复 v1。

项目将这些责任分给不同对象：

对象 保存内容与用途
候选工作区 revisions/<UUID> 一轮工作使用的独立目录，包含源码及构建产物
活动指针 active.json 标识当前提供预览的工作区，以及上一个活动工作区
版本快照 snapshots/vN 为历史版本保存文件，支持后续恢复和读取
源码归档 archives/*.zip 面向下载的源码包，排除依赖与构建目录
数据库 SandboxVersion 保存版本编号、文件路径、构建状态和摘要等元数据

其中工作区的 UUID 与用户看到的 v1、v2 不是同一个编号。UUID 用于定位目录，数字版本用于业务历史；恢复旧版本时会创建新的工作区 UUID，但业务上切回所选历史版本。

从模板到一个可预览版本

项目早期已提供从模板创建工作区、克隆活动工作区和从快照创建工作区三种入口。首次生成从模板开始，后续编辑可以基于现有源码复制，而不是直接覆盖当前预览目录。

下面概括的是正常成功路径，具体的 Agent 计划与角色编排不在本文范围内：

    flowchart TD
  A[模板或活动版本源码] --> B[创建独立候选工作区]
  B --> C[修改源码并执行构建与适用验收]
  C --> D{是否满足发布条件}
  D -->|否| E[不切换活动预览]
  D -->|是| F[保存版本快照和源码 ZIP]
  F --> G[写入活动指针]
  G --> H{数据库持久化是否成功}
  H -->|否| I[尝试恢复旧指针并抛出错误]
  H -->|是| J[清理多余工作区]
  J --> K[预览读取新的活动工作区]

活动指针为何单独保存

预览读取先解析活动工作区，再从其 dist 中取文件。因此，“哪个候选目录正在接受修改”和“哪个目录正在向用户提供游戏”可以分开。

写入时，代码创建同目录临时文件，使用独占创建模式写入 JSON，执行文件同步、关闭，然后重命名为 active.json。这个顺序减少直接覆盖时读到半份 JSON 的机会。它仍受文件系统语义影响，也不能据此承诺断电后文件和数据库一定完全一致。

底层 publishSandboxWorkspace() 还检查工作区路径与 revision 是否对应，并要求 dist/index.html 存在。这个检查只证明发布入口文件可读，不能证明游戏逻辑正确；构建和运行验收应由上层完成。

源码 ZIP 和历史预览不是同一种产物

源码下载需要 src、配置及依赖描述，却不需要携带整个 node_modules。项目的归档遍历排除 node_modules、dist、.agent、archives 和 snapshots，并拒绝遇到的符号链接。

历史预览则需要已经构建的文件。仅保存源码，未来恢复时还可能遇到依赖不可用、构建环境变化，或者原构建产物已被清理的问题。

这也是核对历史代码时发现的一个区别：早期后端 snapshotSandboxSource() 只复制源码；当前 Agent 使用的同名函数在源码复制后，额外复制候选工作区的 dist 到快照中。今天正常生成版本的保存调用来自 Agent，因此历史版本能够一并保存构建产物，源码 ZIP 仍然排除 dist。

同名模块分布在后端与 Agent 两处，阅读时必须确认真实调用来源。只看其中一份，容易错误地推断所有快照是否都包含预览文件。对于只含源码的旧快照，也不能仅凭数据库有一条版本记录就假定它可直接恢复为可玩的游戏。

文件系统与数据库怎样一起发布

文件指针切换与数据库提交无法直接放进同一个普通数据库事务。早期的 publishSandboxWorkspaceAndPersist() 采用失败补偿，关键逻辑是：

persist() 由调用方传入，可以执行版本记录、项目当前版本等数据库更新。它失败时，包装函数尝试恢复之前的文件指针。

这是一种明确的补偿机制，并非文件与数据库的跨系统原子事务：两步之间存在短暂窗口，进程崩溃可能来不及补偿，恢复指针本身也可能失败。评估可靠性时需要知道这些边界，不能把 try/catch 等同于彻底解决一致性。

正常完成后，工作区清理只保留活动 revision 与上一个 revision。历史恢复依靠 snapshots/vN 等版本产物，不依靠永久保留所有候选目录。反过来说，快照和归档也需要独立的容量与保留策略，工作区清理不能替代整套历史数据管理。

恢复历史版本走什么流程

当前后端恢复入口在 apps/backend/src/projects/projects.service.ts，其主要步骤是：

  1. 检查项目所有权，拒绝在已有排队或运行中的 Agent 任务时恢复。
  2. 查找指定的成功版本，从它的快照复制出新的工作区。
  3. 若记录有 previewPath，复制对应预览目录到新工作区的 dist。
  4. 通过同一发布包装函数切换活动指针，在数据库事务中更新 activeSandboxVersion，并记录系统恢复消息。

恢复不是让正在编辑的目录直接退回旧状态。先复制一个新工作区，可以让已保存的历史快照继续作为恢复来源。若历史预览文件已经缺失，恢复仍会失败，元数据存在不等于磁盘产物完整。

预览文件接口还会检查项目所有权，并设置 private, no-store。对于普通生成项目，它从活动工作区读取 dist；导入项目另有预览分支。Sandbox 内部版本保存也不同于社区公开上架，两者不能混称为同一次发布。

今天的核对与验证范围

今天通过 Git 对照确认了上述三份后端基础文件与 8 月提交一致，并阅读当前 Agent 的快照保存、发布调用及后端恢复和预览入口。没有修改项目代码或用户游戏，也没有调用付费模型。

另外重跑了已有的本地文件系统初始化测试：

测试通过，覆盖首次初始化、旧目录源码保护、活动 revision 丢失和仅有构建产物等场景。它使用临时目录验证初始化边界，并不覆盖真实数据库事务、Docker 构建、发布失败补偿或浏览器试玩。本文对这些流程的说明来自源码核对，不能把这次局部测试写成完整端到端验收。

可复用的经验与结论

这套早期设计最值得保留的是职责边界：候选工作区用于修改，活动指针用于提供当前预览，快照用于恢复，源码 ZIP 用于交付，数据库用于检索业务历史。每一层回答的问题都不同。

落地时尤其要检查三点：恢复所需的构建产物是否真的保存；失败补偿能覆盖哪些故障；路径校验、符号链接检查与上层访问权限是否一起生效。词法路径检查只是其中一层，不能单独充当完整执行隔离。

即使以后 Agent 的模型、工具或规划方式继续变化，这些版本基础仍有价值：用户的游戏能持续可玩，修改有独立落点，历史有明确来源，失败也有可以定位和恢复的边界。
