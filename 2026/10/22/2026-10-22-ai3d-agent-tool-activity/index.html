AI 游戏生成的工具执行看得见：并行调用、失败识别与状态恢复

发表于2026-10-22|更新于2026-10-22|AI 3D 游戏生成
|总字数:2k|阅读时长:6分钟|浏览量:|评论数:

生成一个 3D 游戏需要等待：Agent 会读源码、搜索示例、修改组件、构建、截图评审，最后发布。用户看到一个一直旋转的加载图标，很难判断它正在有效推进，还是停在某个失败操作上。

10 月 21 日，项目新增了聊天栏工具执行状态。这次改造把工具调用的开始、完成和失败变成结构化事件，再由前端还原当前操作与最近执行记录。本文基于当天本地源码和离线测试复盘；这些修改仍有未提交部分，不能把本文当成线上完整生成验收报告。

从一个加载图标，到可核对的执行事实

目标很具体：聊天输入框上方显示当前操作，展开后能看到最近 12 项操作、角色和完成耗时。涉及的操作包括读取源码、安装组件、更新计划、构建、评审与发布。

流程不是让模型自己撰写“我正在做什么”，而是在真实工具处理函数外包一层活动中间件。工具处理前发送 started，返回后检查结果，再发送 completed 或 failed。现有会话事件持久化及 Socket 推送负责传递状态，断线后沿用 recent 轮询链路补取事件。

    flowchart TD
  A[模型选择工具] --> B[检查任务是否仍有效]
  B --> C[记录 started：角色、工具、调用 ID]
  C --> D[执行真实工具或内部处理分支]
  D --> E{返回结果是否失败}
  E -->|否| F[记录 completed 与耗时]
  E -->|是或抛出异常| G[记录 failed 与耗时]
  F --> H[现有事件存储与 Socket 推送]
  G --> H
  H --> I[前端按角色与调用 ID 还原状态]
  I --> J[当前操作提示与最近执行记录]

图中的关键边界是 D：工具发现、参数检查或任务契约可能直接处理、拒绝一次调用，不一定执行原始工具函数。活动中间件必须包住这些分支，否则用户会看到部分操作凭空消失。

难点一：并行与父子调用不能共用一个“当前工具”变量

Supervisor 委派开发任务后，父层的 task 调用可能仍在执行；子 Agent 又同时读取两个文件。如果仅保存一个工具名，任意一个读取操作完成，就可能把另一个仍在运行的操作清掉。

当前实现用 actor + callId 标识一次操作，前端保存在 Map 中。结束事件只更新对应条目，不关闭其他角色或其他调用。

当前状态提示优先展示最近的非 task 操作，这样用户看到的是“游戏开发助手正在读取源码”，而不只是长期停留的“委派专业任务”。如果只剩父层委派仍在运行、最新事件又进入模型阶段，则展示“正在分析下一步操作”。同时保留进行中的操作数量，避免把多任务误呈现成单线程。

这段设计适用于任何有并行工具和子 Agent 的应用。调用身份必须明确到一次操作，不能只用工具名配对。实现还为缺少 callId 的旧事件保留工具名回退，但它不具备新事件同等的并行区分能力。

难点二：函数返回，不代表工具成功

很多工具不会抛异常，而是返回 { ok: false }；框架也可能把错误装进 ToolMessage 或命令返回值中。若只在 catch 中记录失败，界面会把这些失败显示成绿色完成。

项目的 isFailedToolResult() 检查几种已知返回协议：顶层 status: "error"、ok: false、命令更新中的消息，以及文本内容里可以解析的 JSON ok: false。异常路径则先记录 failed，再继续抛出原错误。

这是协议识别，不是任意自然语言的语义判断。一个工具若只返回“出错了”这样的普通文本，当前检测不会自动判为失败。因此新增工具时，应统一使用结构化成功/失败字段，让执行器、日志和界面共享一套事实。

难点三：暂停和恢复之后，旧 started 不能继续转圈

实时消息不总能成对抵达：任务停止时可能只有 started，浏览器断线也可能暂时看不到结束事件。恢复任务后若照搬旧记录，界面就会出现几个永远不结束的操作。

前端收到 run.paused 或 run.resumed 时，会把仍在 running 的历史条目标记为 stopped。展示层还用整个任务状态兜底：任务进入终态后，残留条目不再显示为运行中；用户请求停止时，提示等待执行器停止并保存进度。

    stateDiagram-v2
  [*] --> running: started
  running --> completed: completed
  running --> failed: failed
  running --> stopped: paused 或 resumed
  completed --> [*]
  failed --> [*]
  stopped --> [*]

这里的 stopped 表示本轮历史操作不再作为当前活动展示，不应被解释成工具已经完成。恢复是一条新的执行边界，不等于把旧图标重新点亮。

耗时与信息边界也需要说清楚

中间件在发布 started 之前启动 performance.now() 计时，在工具返回后计算毫秒数。因此这是该操作包装范围内的端到端耗时，不是纯 CPU 时间，也不是模型思考时间；委派操作还包含子 Agent 执行时间。

公开事件只带角色、工具名、调用标识和耗时，没有直接转发工具参数、源码、异常正文或模型内部推理。前端再把内部角色名映射成“游戏开发助手”等可读名称。这样用户获得的是理解任务进展所需的信息，而不是被整份调试输出淹没。

同时，role="status" 和 aria-live="polite" 让状态变化可被辅助技术感知，动画受减少动态效果偏好约束。这些细节使执行状态成为可用的交互，而不是单纯装饰。

本次验证与仍需补齐的证据

今天在项目现有依赖下实际运行了两组定向离线测试，均通过：

Agent 侧使用假模型和真实中间件，验证工具发现短路、结构化失败、异常失败、耗时以及事件内容隔离。Web 侧验证并行和父子调用、模型阶段切换、失败提示、恢复、终态，以及服务端静态渲染中的无障碍标记。

这些结果证明了所测事件协议和展示逻辑，但不等于在浏览器里完成了一次真实 LLM 生成、断线重连和 Docker 构建发布。后续应补充一次完整任务的浏览器验收，特别检查断线补取、长时间执行和暂停恢复时的可见状态。

结论：把进度建立在真实调用之上

这次改造最值得复用的是三个原则：一次调用有独立身份，失败按结构化协议识别，暂停恢复有明确的生命周期边界。它们让工具执行记录能与实际运行相互核对，也让用户知道当前值得继续等待，还是需要查看失败记录。

对于 AI 3D 游戏生成这样耗时且包含多个阶段的流程，可理解的执行状态是交付体验的一部分。下一步可以在完整链路验收的基础上，继续完善长耗时提示和失败后的可操作说明。
